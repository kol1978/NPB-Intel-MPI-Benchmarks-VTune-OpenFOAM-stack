## Быстрый старт

### 1. Установка скрипта

```bash
cp runIso3dfd ~/OpenFOAM/kol-v2312/applications/PARALLELISM/oneAPI-samples/DirectProgramming/C++/StructuredGrids/iso3dfd_omp_offload/runIso3dfd
chmod +x ~/OpenFOAM/kol-v2312/applications/PARALLELISM/oneAPI-samples/DirectProgramming/C++/StructuredGrids/iso3dfd_omp_offload/runIso3dfd
```

### 2. Запуск

```bash
cd ~/OpenFOAM/kol-v2312/applications/PARALLELISM/oneAPI-samples/DirectProgramming/C++/StructuredGrids/iso3dfd_omp_offload
./runIso3dfd
```

Скрипт интерактивно спросит режим запуска и создаст уникальную папку с результатами.

### 3. Требования

- **Компилятор**: Intel LLVM (icpx) 2026.1.1 — `/opt/intel/oneapi/compiler/2026.1/bin`
- **Бинарник**: `./build/src/iso3dfd` (собран с `NO_OFFLOAD=ON`)
- **VTune**: `/opt/intel/oneapi/vtune/latest` (для режимов 2 и 3)
- **OpenMP**: Intel OpenMP (`-fiopenmp`), включён в поставку icpx
- **GPU**: не требуется (CPU-only режим)

## Описание меню скрипта

При запуске `./runIso3dfd` скрипт выводит:

```
═══════════════════════════════════════════════════════════
  iso3dfd_omp_offload — CPU-only (NO_OFFLOAD=ON)
  Grid:  256 x 256 x 256
  Block: 16 x 8 x 64
  Iterations: 100
  OMP_NUM_THREADS: 24
═══════════════════════════════════════════════════════════

  Режим запуска:
    1) Чистый замер (0% overhead) — точное время
    2) VTune hotspots (~5% HW / ~2× SW) — детальный анализ CPU
    3) APS — Application Performance Snapshot (1–3% overhead)

  Выберите [1-3]:
```

### При выборе режима 3 (APS) — подменю:

```
  APS — режим сбора (--collection-mode):
    a) all  — все метрики: HW + OpenMP (1–3% overhead)
    b) hwc  — только HW-счётчики: CPI, Memory, NUMA, Vectorization (<1%)
    c) omp  — только OpenMP: Imbalance, Serial Time (<1%)

  Выберите [a/b/c]:
```

### Сводная таблица режимов

| Режим | Overhead | Драйвер SEP | Точность времени | Детализация |
|-------|----------|-------------|------------------|-------------|
| 1. Чистый замер | 0% | не нужен | максимальная | только метрики iso3dfd |
| 2. VTune hotspots | ~5% (HW) / ~2× (SW) | HW: нужен, SW: нет | искажена | per-function, call stack |
| 3a. APS all | 1–3% | не нужен | почти точная | CPI, Memory, NUMA, OpenMP |
| 3b. APS hwc | <1% | не нужен | почти точная | CPI, Memory, NUMA, Vectorization |
| 3c. APS omp | <1% | не нужен | почти точная | OpenMP Imbalance, Serial Time |

## Режимы запуска — подробное описание

### Режим 1: Чистый замер (без профилирования)

**Команда:**
```bash
OMP_NUM_THREADS=24 ./iso3dfd 256 256 256 16 8 64 100
```

**Overhead:** 0%

**Что происходит:**
- Прямой запуск `iso3dfd` без внешних инструментов
- Программа сама измеряет время kernel-цикла и считает метрики
- Результат пишется в лог и в `log.timing` (накапливается)

**Что показывает:**

| Метрика | Единица | Описание |
|---------|---------|----------|
| `time` | сек | Время выполнения kernel-цикла (100 итераций) |
| `throughput` | Mpts/s | Миллионов точек сетки в секунду |
| `flops` | GFlops | Гигафлопс — вычислительная производительность |
| `bytes` | GBytes/s | Пропускная способность памяти |

**Пример вывода:**
```
Grid Sizes: 256 256 256
Tile sizes ignored for OMP Offload
--Using Baseline version with omp target with collapse
Memory Usage (MBytes): 230
--------------------------------------
time         : 2.96 secs
throughput   : 566.798 Mpts/s
flops        : 34.5747 GFlops
bytes        : 6.80157 GBytes/s
--------------------------------------
```

**Когда использовать:**
- Сравнение разных размеров сетки (256³ vs 512³)
- Сравнение разных размеров блока (16×8×64 vs 32×8×1)
- Сравнение числа потоков (12 vs 24)
- Baseline-замеры для V&V-документа
- Любой замер, где важна точность времени

### Режим 2: VTune hotspots

**Команда:**
```bash
vtune -quiet -collect hotspots \
    -knob sampling-mode=sw \
    -knob enable-characterization-insights=false \
    -finalization-mode=deferred \
    -r <result_dir> \
    -- ./iso3dfd 256 256 256 16 8 64 100
```

**Overhead:** ~5% (HW sampling) или ~2× (SW sampling, как в скрипте)

**Что происходит:**
- VTune запускает `iso3dfd` под своим контролем
- SW sampling: VTune использует `SIGPROF` (10 мс интервал) для сбора образцов
- После запуска — отложенная финализация (`-finalization-mode=deferred`), экономит ~23 сек
- Затем — отдельный шаг финализации и генерация отчётов

**Что показывает:**

| Метрика | Описание |
|---------|----------|
| **Top-10 функций** | Какие функции занимают больше всего CPU time |
| **CPU time vs Wait time** | Сколько времени CPU считал, а сколько ждал |
| **Per-thread timeline** | Загрузка каждого потока OpenMP |
| **Call stack** | Дерево вызовов для каждой горячей точки |
| **Source-level attribution** | Привязка времени к строкам исходного кода |

**Пример вывода (summary):**
```
Elapsed Time: 5.82s
CPU Time:     5.71s
Slots:        98.1%
```

**Пример вывода (top-10 hotspots):**
```
Function                        CPU Time    % of Elapsed
iso3dfd_cpu_nocache_block       4.12s       70.8%
Initialize                      0.43s        7.4%
...
```

**Когда использовать:**
- APS показал проблему, нужно понять — какая именно функция виновата
- Нужно посмотреть call stack для горячей точки
- Нужно привязать время к строкам исходного кода
- Анализ OpenMP-дисбаланса на уровне потоков

**Когда НЕ использовать:**
- Нужен точный замер времени (overhead ~2× для коротких запусков)
- Нужно сравнить производительность разных конфигураций (время искажено)
- Короткие запуски (< 10 сек) — SW sampling даёт мало образцов

**Ограничения:**
- SW sampling: 10 мс интервал → для 3-секундного запуска всего ~300 образцов
- HW sampling: нужен SEP-драйвер (установка требует root)
- Большие объёмы данных при множественных запусках

### Режим 3a: APS — collection-mode=all

**Команда:**
```bash
aps --collection-mode=all --result-dir=<result_dir> -- ./iso3dfd 256 256 256 16 8 64 100
```

**Overhead:** 1–3%

**Что происходит:**
- APS (Application Performance Snapshot) — лёгкий профилировщик из состава VTune
- Собирает HW-счётчики CPU (через `perf` API, без SEP-драйвера)
- Параллельно трассирует OpenMP-регионы (через Intel OpenMP runtime)
- После запуска — генерация консольного и HTML-отчёта

**Что показывает:**

#### Аппаратные метрики (HW counters)

| Метрика | Описание | Норма для HPC |
|---------|----------|---------------|
| **CPI** (Cycles Per Instruction) | Сколько тактов CPU тратит на одну инструкцию | 0.5–1.0 — отлично; 1.0–2.0 — приемлемо; > 2.0 — проблема |
| **Memory Stalls** | Доля тактов, потерянных на ожидание памяти (cache + DRAM) | < 20% — хорошо; > 50% — memory-bound |
| **Cache Stalls** | Разбивка: L1/L2/L3 cache misses | Зависит от размера кэша CPU |
| **DRAM Stalls** | Разбивка: ожидание DRAM (дальних доступов) | Чем меньше, тем лучше |
| **NUMA ratio** | Доля удалённых доступов к памяти (с другого NUMA-узла) | < 10% — хорошо; > 30% — NUMA-проблема |
| **Vectorization** | Процент векторизованных FP-операций (AVX2/AVX-512) | > 80% — хорошо; < 50% — код не векторизован |
| **SP GFLOPS** | Single-precision GFLOPS (аппаратные) | Сравнение с метрикой `iso3dfd` |
| **CPU Utilization** | Загрузка всех логических ядер | 90–100% — хорошо; < 70% — дисбаланс или I/O |

#### OpenMP-метрики

| Метрика | Описание | Норма |
|---------|----------|-------|
| **OpenMP Imbalance** | Доля времени, потерянного на барьерах OpenMP | < 10% — хорошо; > 30% — дисбаланс потоков |
| **Serial Time** | Время вне OpenMP-регионов (однопоточное) | < 5% — хорошо; > 20% — слишком много serial-кода |

#### Метрики памяти

| Метрика | Описание |
|---------|----------|
| **Memory Footprint (max)** | Максимальное потребление resident memory одним процессом |
| **Memory Footprint (avg)** | Среднее потребление resident memory |
| **Virtual Memory** | Потребление виртуальной памяти |

**Пример вывода APS:**
```
==================================================================
                      APS Report
================================================================--

Elapsed Time:                    3.04 sec
CPU Utilization:                 23.9 cores (99.6%)
SP GFLOPS:                      34.21
CPI:                            0.87

--- Memory Bandwidth & Stalls ---
Memory Stalls:                  18.3%
  -- L2 Stalls:                  8.1%
  -- L3 Stalls:                  6.2%
  -- DRAM Stalls:                4.0%

--- NUMA ---
NUMA ratio:                      0.02 (2.0%)

--- Vectorization ---
Vectorization:                  91.2%
  -- 128-bit:                    8.8%
  -- 256-bit:                   82.4%
  -- 512-bit:                    0.0%

--- OpenMP ---
OpenMP Imbalance:                3.1%
Serial Time:                     1.2%

--- Memory Footprint ---
Max RSS:                        235.4 MB
Avg RSS:                        232.1 MB
```

**Когда использовать:**
- Быстрая оценка: memory-bound или compute-bound?
- Проверка NUMA-локальности (критично для 2-сокетного Xeon)
- Проверка векторизации (AVX2 vs AVX-512)
- Проверка OpenMP-дисбаланса
- Оценка потребления памяти
- Регулярный мониторинг (низкий overhead — можно запускать часто)

**Overhead:** < 1%

## Что показывает каждый режим и как анализировать

### Анализ режима 1: Чистый замер

#### Что смотреть

1. **time** — время kernel-цикла. Сравнивайте только между запусками с одинаковыми параметрами.

2. **throughput (Mpts/s)** — главный показатель эффективности. Чем выше, тем лучше.
   - 256³ = 16.7M точек (без halo) → throughput = 16.7M / time
   - Сравнивайте разные размеры блока — лучший блок даёт максимальный throughput

3. **flops (GFlops)** — вычислительная производительность.
   - 9 коэффициентов × 2 операции (умножение + сложение) × 6 направлений = 108 flop/точку
   - Теоретический пик для 24 ядер × AVX2 (8 FP/cycle) × 2.5 GHz = 480 GFlops
   - 34.6 GFlops = 7.2% от пика — нормально для memory-bound stencil

4. **bytes (GBytes/s)** — пропускная способность памяти.
   - Для 2-сокетного Xeon: теоретический пик ~80–100 GBytes/s
   - 6.8 GBytes/s = ~7–8.5% от пика — stencil 16-го порядка переиспользует данные в кэше

#### Как анализировать

```
time=2.96, throughput=566.8 Mpts/s, flops=34.6 GFlops, bytes=6.8 GBytes/s
```

- **throughput высокий, flops низкий** → memory-bound (данные не успевают поступать)
- **throughput низкий, flops высокий** → compute-bound (мало вычислений на точку)
- **bytes близок к пику памяти** → упёрлись в пропускную способность DRAM
- **bytes далеко от пика** → данные лежат в кэше (хорошо для stencil)

---

### Анализ режима 2: VTune hotspots

#### Что смотреть

1. **Top-10 функций** — какая функция занимает больше всего CPU time.
   - Для `iso3dfd` ожидаемо: `iso3dfd_cpu_nocache_block` или `iso3dfd_cpu_cache_block`
   - Если неожиданная функция в топе — проблема в архитектуре кода

2. **CPU Time vs Elapsed Time**:
   - CPU Time ≈ Elapsed × NP → хорошая утилизация
   - CPU Time << Elapsed × NP → потоки простаивают

3. **Per-thread timeline** (в GUI):
   - Ровные полосы → все потоки загружены равномерно
   - Зубцы → дисбаланс (одни потоки ждут на барьерах, другие работают)

4. **Wait Time** (в summary):
   - High Wait Time + Low CPU Time → синхронизация или I/O
   - Low Wait Time + High CPU Time → чистые вычисления

#### Как анализировать

```
Function                    CPU Time    % of Elapsed
iso3dfd_cpu_nocache_block   4.12s       70.8%
Initialize                  0.43s        7.4%
```

- 70.8% в одной функции — нормально для stencil (всё время — вычисления)
- Если Initialize > 20% — проблема в инициализации (нужно вынести из замера)
- Если много мелких функций в топе — код фрагментирован, возможен overhead вызовов

### Анализ режима 3: APS

#### CPI (Cycles Per Instruction)

| CPI | Интерпретация | Действие |
|-----|---------------|----------|
| 0.25–0.5 | Отлично (полная конвейеризация) | Ничего не делать |
| 0.5–1.0 | Хорошо (норма для HPC) | Оптимально для stencil |
| 1.0–2.0 | Приемлемо, но есть проблемы | Проверить Memory Stalls |
| > 2.0 | Плохо — много простоя | Memory-bound или branch misprediction |

Для stencil 16-го порядка CPI ~0.87 — нормально: код состоит из умножений и сложений, которые хорошо конвейеризуются, но зависят от данных из памяти.

#### Memory Stalls

| Memory Stalls | Интерпретация |
|---------------|---------------|
| < 10% | Отлично — данные в кэше |
| 10–20% | Хорошо — stencil переиспользует кэш |
| 20–40% | Данные частично уходят в DRAM |
| > 40% | Memory-bound — основное время ждём память |

Разбивка:
- **L2 Stalls > L3 Stalls** → рабочий набор не помещается в L1, но помещается в L2/L3
- **L3 Stalls > DRAM Stalls** → данные в L3, но не в L1/L2 — типично для stencil
- **DRAM Stalls > 10%** → данные уходят в DRAM — нужно увеличить размер блока

#### NUMA ratio

| NUMA ratio | Интерпретация | Действие |
|------------|---------------|----------|
| < 5% | Отлично — данные локальны | Ничего не делать |
| 5–15% | Приемлемо | Проверить `numactl --membind` |
| > 15% | Плохо — данные на удалённом узле | Использовать `numactl --membind=0 --cpunodebind=0` |

Для 2-сокетного Xeon: если `iso3dfd` запущен без `numactl`, ОС может разместить данные на любом NUMA-узле. NUMA ratio > 15% означает, что половина обращений уходит на другой сокет — пропускная способность падает в 2–3 раза.

#### Vectorization

| Vectorization | Интерпретация |
|---------------|---------------|
| > 90% | Отлично — код полностью векторизован |
| 50–90% | Приемлемо — часть кода скалярная |
| < 50% | Плохо — код не использует SIMD |

Разбивка по ширине:
- **128-bit (SSE)** — устаревший, AVX не работает
- **256-bit (AVX2)** — стандарт для современных Xeon
- **512-bit (AVX-512)** — максимальная производительность (если CPU поддерживает)

Для `iso3dfd` с `-O3` и icpx: ожидается 80–95% векторизации, преимущественно 256-bit (AVX2). Если 512-bit = 0% — либо CPU не поддерживает AVX-512, либо компилятор не решился на него. В этом случае можно попробовать `-xCORE-AVX512` или `-xHOST`.

#### OpenMP Imbalance

| Imbalance | Интерпретация |
|-----------|---------------|
| < 5% | Отлично — потоки сбалансированы |
| 5–15% | Приемлемо — небольшой дисбаланс |
| > 15% | Плохо — потоки ждут на барьерах |

Причины дисбаланса:
- Размер блока не делится на число потоков → последний поток делает меньше работы
- `OMP_SCHEDULE=static` → фиксированное распределение, не учитывает нагрузку
- Решение: попробовать `OMP_SCHEDULE=dynamic` или изменить размер блока

#### Serial Time

| Serial Time | Интерпретация |
|-------------|---------------|
| < 5% | Отлично — почти всё время в OpenMP |
| 5–15% | Приемлемо — инициализация, I/O |
| > 15% | Плохо — слишком много однопоточного кода |

Для `iso3dfd` ожидается: 1–3% (инициализация массивов перед kernel-циклом).

#### Memory Footprint

| Метрика | Что показывает |
|---------|----------------|
| Max RSS | Пиковое потребление памяти одним процессом |
| Avg RSS | Среднее потребление (стабильная часть) |

Для `iso3dfd` с сеткой 256³: 3 массива × 256³ × 4 байта = 3 × 64 MB = 192 MB + overhead → ~230 MB.

Это нужно для оценки:
- Поместится ли сетка в RAM при увеличении размера
- Сколько памяти нужно для OpenFOAM (где сетки обычно крупнее)
- При планировании декомпозиции: сколько рангов можно разместить на узле

## Параметры командной строки iso3dfd

| Позиция | Имя | Значение по умолчанию | Описание |
|---------|-----|-----------------------|----------|
| 1 | `n1` | 256 | Размер сетки по оси X |
| 2 | `n2` | 256 | Размер сетки по оси Y |
| 3 | `n3` | 256 | Размер сетки по оси Z |
| 4 | `n1_block` | 16 | Размер блока (тайла) по X |
| 5 | `n2_block` | 8 | Размер блока (тайла) по Y |
| 6 | `n3_block` | 64 | Размер блока (тайла) по Z |
| 7 | `Iterations` | 100 | Число шагов по времени |

### Влияние параметров на производительность

| Параметр | Эффект |
|----------|--------|
| Сетка 256³ → 512³ | Время × 8, память × 8, throughput примерно тот же |
| Сетка 1024³ | Память ~1.5 GB — может не поместиться в кэш, throughput упадёт |
| Block 16×8×64 → 32×8×64 | Меньше блоков → меньше overhead OpenMP, но больше давление на кэш |
| Block 16×8×64 → 16×16×64 | Изменение геометрии блока — влияет на переиспользование кэша |
| Iterations 100 → 1000 | Время × 10, throughput стабилизируется (меньше влияния инициализации) |

## Управление числом потоков OpenMP

### Стандартные варианты

```bash
# Все ядра (по умолчанию)
OMP_NUM_THREADS=$(nproc) ./src/iso3dfd 256 256 256 16 8 64 100

# Ограничить число потоков
OMP_NUM_THREADS=12 ./src/iso3dfd 256 256 256 16 8 64 100

# Один NUMA-узел (рекомендуется для 2-сокетных систем)
numactl --membind=0 --cpunodebind=0 \
    OMP_NUM_THREADS=12 ./src/iso3dfd 256 256 256 16 8 64 100
```

### Через переменные окружения скрипта

```bash
# Переопределение параметров
OMP_THREADS=12 GRID_X=512 GRID_Y=512 GRID_Z=512 ./runIso3dfd

# Полный набор
OMP_THREADS=12 GRID_X=256 GRID_Y=256 GRID_Z=256 \
BLK_X=32 BLK_Y=8 BLK_Z=64 ITERATIONS=200 ./runIso3dfd
```

### Schedule (распределение итераций)

```bash
# Static — по умолчанию, лучший для равномерной нагрузки
OMP_SCHEDULE=static OMP_NUM_THREADS=24 ./src/iso3dfd 256 256 256 16 8 64 100

# Dynamic — для неравномерной нагрузки (если OpenMP Imbalance > 15%)
OMP_SCHEDULE=dynamic,4 OMP_NUM_THREADS=24 ./src/iso3dfd 256 256 256 16 8 64 100
```

## Сценарии использования

### Сценарий 1: Baseline-замер

**Цель:** получить эталонные метрики для сравнения.

```bash
./runIso3dfd
# Выбрать: 1 (Чистый замер)
```

Результат: точные time, throughput, GFlops, GBytes/s в `log.timing`.

### Сценарий 2: Проверка NUMA-локальности

**Цель:** понять, не теряет ли производительность из-за межсокетных пересылок.

```bash
# Без numactl (по умолчанию)
./runIso3dfd
# Выбрать: 3 → a (APS all)

# С numactl (привязка к одному NUMA-узлу)
numactl --membind=0 --cpunodebind=0 OMP_THREADS=12 ./runIso3dfd
# Выбрать: 3 → a (APS all)
```

Сравнить `NUMA ratio` между запусками:
- Без `numactl`: если NUMA ratio > 15% — данные размазаны по двум сокетам
- С `numactl`: NUMA ratio должен быть < 5%

### Сценарий 3: Поиск оптимального размера блока

**Цель:** найти размер блока, дающий максимальный throughput.

```bash
# Блок 16×8×64
BLK_X=16 BLK_Y=8 BLK_Z=64 ./runIso3dfd   # режим 1

# Блок 32×8×64
BLK_X=32 BLK_Y=8 BLK_Z=64 ./runIso3dfd   # режим 1

# Блок 16×16×64
BLK_X=16 BLK_Y=16 BLK_Z=64 ./runIso3dfd  # режим 1

# Блок 64×8×32
BLK_X=64 BLK_Y=8 BLK_Z=32 ./runIso3dfd   # режим 1
```

Сравнить `throughput` и `time` в `log.timing`. Затем лучший вариант проверить через APS (режим 3) — убедиться, что Memory Stalls и OpenMP Imbalance минимальны.

### Сценарий 4: Проверка векторизации

**Цель:** убедиться, что компилятор векторизовал код.

```bash
./runIso3dfd
# Выбрать: 3 → b (APS hwc, только HW-счётчики)
```

Смотреть `Vectorization`:
- Если < 50% — код скалярный, нужно пересобрать с `-O3` или добавить прагмы
- Если 256-bit = 100%, 512-bit = 0% — CPU не поддерживает AVX-512 или компилятор не решился
- Для включения AVX-512: пересобрать с `-xCORE-AVX512` или `-xHOST`

### Сценарий 5: Диагностика низкого throughput

**Цель:** понять, почему throughput ниже ожидаемого.

**Шаг 1:** APS all (режим 3 → a)
- CPI > 1.5? → проблема в инструкциях (branch, зависимости)
- Memory Stalls > 40%? → memory-bound, увеличить блок
- NUMA ratio > 15%? → использовать `numactl`
- Vectorization < 50%? → пересобрать с векторизацией
- OpenMP Imbalance > 15%? → изменить `OMP_SCHEDULE` или размер блока

**Шаг 2:** VTune hotspots (режим 2)
- Какая функция в топе? Должна быть `iso3dfd_cpu_*`
- Есть ли unexpected функции (initialize, memcpy)?
- Per-thread timeline: есть ли простаивающие потоки?

### Сценарий 6: Scaling-тест (по числу потоков)

**Цель:** понять, как масштабируется приложение.

```bash
OMP_THREADS=1  ./runIso3dfd   # режим 1
OMP_THREADS=2  ./runIso3dfd   # режим 1
OMP_THREADS=4  ./runIso3dfd   # режим 1
OMP_THREADS=8  ./runIso3dfd   # режим 1
OMP_THREADS=12 ./runIso3dfd   # режим 1
OMP_THREADS=24 ./runIso3dfd   # режим 1
```

Построить график throughput от числа потоков:
- Линейный рост → отличная масштабируемость
- Рост с насыщением после 12 потоков → упёрлись в пропускную способность памяти одного NUMA-узла
- Плато после 12 → NUMA-эффект (второй сокет не помогает)

### Сценарий 7: Сравнение с OpenFOAM

**Цель:** использовать `iso3dfd` как референс для оценки OpenFOAM.

```bash
# iso3dfd baseline
./runIso3dfd   # режим 1

# iso3dfd с APS
./runIso3dfd   # режим 3 → a

# OpenFOAM с APS (через MPI)
source /opt/intel/oneapi/vtune/latest/apsvars.sh
mpirun -n 24 aps ./solver -parallel
aps --report ./aps_result_*
```

Сравнить:
- CPI: `iso3dfd` обычно ниже (проще код) → если OpenFOAM CPI > 2× — сложный код
- Memory Stalls: `iso3dfd` ~15–20% → если OpenFOAM > 40% — неэффективный доступ к памяти
- Vectorization: `iso3dfd` ~90% → если OpenFOAM < 50% — код не векторизован
- NUMA ratio: сравнить с `numactl` и без
