# Отчёт по бенчмаркам iso3dfd: MPI, OpenMP, NUMA, масштабирование

**Сервер:** kol-serv  
**ОС:** Ubuntu 24.04, ядро 7.0.0-34-generic  
**CPU:** Intel Xeon X5675 (Westmere-EP), 2 сокета, 2 NUMA-узла, 12 физических / 24 логических ядра  
**Компилятор:** Intel oneAPI (icpx)  
**MPI:** Intel MPI (I_MPI_PIN, I_MPI_PIN_DOMAIN)  
**OpenMP:** OMP_NUM_THREADS, OMP_PROC_BIND=close, OMP_PLACES=cores  

---

## 1. Цель

Определить оптимальную гибридную конфигурацию MPI+OpenMP для stencil-кода iso3dfd (3D изотропный волновой оператор 16-го порядка) на двухузловой NUMA-системе. Критерии оптимизации — максимальная производительность (GFLOPS) и вычислительная эффективность (отношение к последовательному базовому варианту).

---

## 2. Архитектура целевой платформы

### 2.1. Иерархия памяти

| Уровень | Объём | Разделение | Полоса (оценка) |
|---------|-------|-----------|-----------------|
| L1d | 32 КБ | на ядро | ~1 ТБ/с |
| L2 | 256 КБ | на ядро | ~400 ГБ/с |
| L3 | 12 МБ | на сокет (6 ядер) | ~200 ГБ/с |
| DDR3 | 48 ГБ | на сокет (3 канала) | ~32 ГБ/с |
| QPI | — | межсокетная шина | 25,6 ГБ/с |

### 2.2. Параметры стенсила

| Параметр | Значение |
|----------|----------|
| Порядок стенсила | 16 (half-length = 8) |
| Радиус | 8 точек в каждом направлении |
| Число точек стенсила | \(1 + 3 \times 2 \times 8 = 49\) |
| Коэффициенты | 9 (симметрия: \(c_0, c_1, \ldots, c_8\)) |
| Вычислений на точку | ~50 FLOP (25 умножений + 25 сложений) |
| Размер элемента | 8 байт (double) |

### 2.3. Арифметическая интенсивность

Арифметическая интенсивность (AI) — отношение числа операций с плавающей точкой к объёму трафика памяти — является ключевым параметром модели Roofline [1]. Для стенсила 16-го порядка:

**Без переиспользования кэша** (наивная реализация, каждая точка загружается из DRAM):

\[
\text{AI}_{\text{DRAM}} = \frac{50}{(49 + 9 + 1 + 1) \times 8} = \frac{50}{480} \approx 0{,}10 \;\text{FLOP/байт}
\]

**При выполнении двумерного условия слоёв (2D Layer Condition)** — только z-направление вызывает промахи кэша, x и y обслуживаются из L1/L2 [2]:

\[
\text{AI}_{\text{2D-LC}} = \frac{50}{3 \times 8} \approx 2{,}08 \;\text{FLOP/байт}
\]

Переход от DRAM-связанного режима (\(\text{AI} = 0{,}10\)) к режиму с выполненным условием слоёв (\(\text{AI} = 2{,}08\)) даёт **20-кратное** увеличение арифметической интенсивности. Это означает, что при правильном блочном разбиении (cache blocking) stencil-код из строго memory-bound может перейти в режим, ограниченный полосой L3 или вычислительным конвейером.

### 2.4. Точка излома Roofline

Для одного сокета Xeon X5675:

| Параметр | Значение |
|----------|----------|
| Пиковая производительность (SSE, 6 ядер) | 73,4 GFLOPS |
| Полоса DDR3 (3 канала, измеренная) | ~32 ГБ/с |
| Точка излома (ridge point) | \(\frac{73{,}4}{32} \approx 2{,}29\) FLOP/байт |

При \(\text{AI} = 0{,}10\) (без кэш-блокинга) код жёстко ограничен полосой DRAM: ожидаемая производительность \(\approx 0{,}10 \times 32 = 3{,}2\) GFLOPS. При \(\text{AI} = 2{,}08\) (2D LC выполнена) код приближается к границе вычислительных возможностей: \(\approx 2{,}08 \times 32 = 66{,}6\) GFLOPS, что выше пика — значит, работающий набор обслуживается из L3, а не из DRAM.

## 3. Условие слоёв (Layer Condition) и анализ рабочего набора

### 3.1. Модель условия слоёв

Модель условия слоёв (Layer Condition, LC), предложенная исследовательской группой RRZE-HPC [2], позволяет оценить требования к кэшу для stencil-кодов. Модель предполагает идеальную политику замещения LRU и использует эвристическое правило: для оценки доступного кэша берётся половина физического объёма (\(C_a = C_s / 2\)).

**Двумерное условие слоёв** для 3D стенсила радиуса \(r\):

\[
S_h \times M_w \times s \leq C_a
\]

где:
- \(S_h = 2r + 1\) — высота стенсила (число плоскостей);
- \(M_w\) — ширина массива в направлении внутреннего цикла;
- \(s\) — размер элемента в байтах;
- \(C_a = C_s / 2\) — применимый объём кэша с запасом.

Для стенсила 16-го порядка (\(r = 8\), \(S_h = 17\)) и размера блока \(64 \times 64\):

\[
17 \times 64 \times 8 = 8{,}704 \;\text{байт} \approx 8{,}5 \;\text{КБ}
\]

Это значение тривиально укладывается в L1 (32 КБ). Таким образом, **двумерное условие слоёв выполняется уже на уровне L1** для блока \(64 \times 64\), что означает: при правильном блочном разбиении обращения по осям x и y обслуживаются из L1, и только z-направление вызывает промахи в нижележащие уровни.

### 3.2. Рабочий набор блока

Блок \(64 \times 64 \times 64\) (блочное разбиение кода iso3dfd):

| Компонент | Объём |
|-----------|-------|
| Данные блока (\(64^3 \times 8\)) | 2,00 МБ |
| Halo, одна сторона (16 слоёв \(\times 64 \times 64 \times 8\)) | 0,50 МБ |
| Halo, обе стороны | 1,00 МБ |
| **Итого рабочий набор на поток** | **~3,00 МБ** |

При распределении блока по \(N\) потокам OpenMP каждый поток обрабатывает подблок \(64 \times 64 \times (64/N)\). Рабочий набор на поток:

| Потоков на ранг | Подблок | Данные на поток | Halo на поток | Всего на поток |
|-----------------|---------|-----------------|---------------|----------------|
| 1 | \(64 \times 64 \times 64\) | 2,00 МБ | 1,00 МБ | 3,00 МБ |
| 2 | \(64 \times 64 \times 32\) | 1,00 МБ | 1,00 МБ | 2,00 МБ |
| 4 | \(64 \times 64 \times 16\) | 0,50 МБ | 1,00 МБ | 1,50 МБ |
| 8 | \(64 \times 64 \times 8\) | 0,25 МБ | 1,00 МБ | 1,25 МБ |

> Примечание: halo остаётся постоянным (16 слоёв), так как радиус стенсила не зависит от числа потоков.

### 3.3. Суммарный рабочий набор на сокет

L3 (12 МБ на сокет) совместно используется 6 ядрами. Эффективный объём с запасом 50%: 6 МБ. Суммарный рабочий набор:

| Конфигурация | Рангов на сокет | Потоков на ранг | Набор на поток | Суммарно на сокет | L3 (6 МБ) | Статус |
|---|---|---|---|---|---|---|
| 12×1 | 6 | 1 | ~2,3 МБ¹ | 13,8 МБ | превышен | вытеснение (thrashing) |
| 6×2 | 3 | 2 | ~2,0 МБ | 6,0 МБ | на границе | предельно |
| 3×4 | 2 | 4 | ~1,5 МБ | 6,0 МБ | на границе | предельно |
| 3×8 | 2 | 8² | ~1,25 МБ | 10,0 МБ | превышен | вытеснение + SMT |
| **2×4** | **1** | **4** | **~1,5 МБ** | **3,0 МБ** | **с запасом** | **оптимально** |

¹ Для 12×1: рабочий набор меньше (20 слоёв/ранг), но 6 рангов одновременно конкурируют за L3.  
² 8 потоков на 6 физических ядер — задействована гиперпоточность (SMT).

**Ключевой вывод:** конфигурация 2×4 — единственная, при которой суммарный рабочий набор (3,0 МБ) существенно меньше эффективного объёма L3 (6 МБ). Это обеспечивает:
- выполнение 2D Layer Condition с двукратным запасом;
- удержание всех вычислительных данных и halo в L3;
- отсутствие вытеснения (cache thrashing) вычислительных данных MPI-буферами;
- обслуживание данных из L3 (~200 ГБ/с) вместо DRAM (~32 ГБ/с).

## 4. Методика

- Сетка: \(256 \times 256 \times N_3\), блок: \(64 \times 64 \times 64\), итераций: 2000, half-length = 8 (стенсил 16-го порядка).
- Метрики: время выполнения (с), производительность (GFLOPS, вычисляется встроенным кодом), размер локальной области (слоёв на ранг), доля полезной области.
- Привязка: `I_MPI_PIN=on`, `OMP_PROC_BIND=close`, `OMP_PLACES=cores`. В ряде экспериментов дополнительно применялся `numactl`.
- Профилирование: VTune (hotspots, sampling-mode=sw) для последовательного режима и ранга 0 через wrapper-скрипт. Основной анализ — по встроенным метрикам кода.

> **Ограничение VTune:** в режиме attach к MPI-процессу не поддерживается в данной версии; стандартный запуск `vtune -- mpirun` вызывает конфликт ptrace/dup2 с Hydra. Для профилирования использовался wrapper-скрипт, перехватывающий только ранг 0. Ввиду этого основным источником количественных данных стали встроенные метрики кода.

### 5.4. Гибридные конфигурации

| Конфигурация | Ядер | Слоёв/ранг | Время (с) | GFLOPS | Эффективность | Рабочий набор / L3 |
|---|---|---|---|---|---|---|
| 3×4 | 12 | 160 | 317,1 | 3,30 | 16,9% | на границе L3 |
| 6×2 (run 1) | 12 | 80 | 137,0 | 3,39 | 17,4% | на границе L3 |
| 6×2 (run 2) | 12 | 80 | 141,9 | 3,27 | 16,8% | на границе L3 |
| 3×8 | 24 | 160 | 245,7 | 4,25 | 21,8% | превышен + SMT |
| **2×4** | **8** | **240** | **186,7** | **8,71** | **55,8%** | **с запасом** |

**Анализ по конфигурациям:**

**2 MPI × 4 OMP (оптимальная).** Один ранг на сокет, четыре потока OpenMP на ранг. Суммарный рабочий набор ~3,0 МБ на сокет — в два раза меньше эффективного объёма L3 (6 МБ). 2D Layer Condition выполняется с запасом, все вычислительные данные и halo удерживаются в L3. MPI-коммуникация минимальна (2 ранга), локальная область максимальна (240 слоёв). Производительность 8,71 GFLOPS — на порядок выше остальных конфигураций.

**3 MPI × 4 OMP.** Два ранга на одном сокете (асимметрия при 3 рангах на 2 сокета). Суммарный рабочий набор ~6,0 МБ — на границе эффективного объёма L3. Производительность 3,30 GFLOPS — в 2,6 раза ниже 2×4 при большем числе ядер.

**6 MPI × 2 OMP.** Три ранга на сокет, рабочий набор ~6,0 МБ — на границе L3. Нестабильность (3,27–3,39 GFLOPS) обусловлена миграцией потоков между NUMA-узлами: `I_MPI_PIN_DOMAIN` не всегда предотвращает миграцию при малом числе потоков на ранг.

**3 MPI × 8 OMP.** Восемь потоков на ранг, но на сокете 6 физических ядер — задействована гиперпоточность (SMT). Суммарный рабочий набор ~10 МБ превышает L3. Накладные расходы SMT и вытеснение кэша снижают производительность до 4,25 GFLOPS, несмотря на использование 24 логических ядер.

## 7. Ключевые выводы

1. **Локальность кэша — первопричина, коммуникации — следствие.** Конфигурация 2×4 превосходит остальные не только за счёт меньшего числа MPI-рангов, но и потому, что суммарный рабочий набор (~3 МБ на сокет) с запасом укладывается в эффективный объём L3 (6 МБ). Это обеспечивает выполнение 2D Layer Condition и поднимает арифметическую интенсивность с 0,10 до ~2,08 FLOP/байт.

2. **Вытеснение кэша (cache thrashing) — основной лимитирующий фактор при большом числе рангов.** При 12 рангах суммарный рабочий набор (~13,8 МБ) превышает L3 (12 МБ). MPI-буферы `Sendrecv` дополнительно вытесняют вычислительные данные, снижая арифметическую интенсивность до уровня DRAM-связанного режима.

3. **Граница масштабирования OpenMP — 4 потока на ранг.** При 8 потоках накладные расходы на синхронизацию и SMT превышают выигрыш от параллелизма. Рабочий набор на поток (1,25 МБ) мал, но суммарный набор (10 МБ) превышает L3 при 2 рангах на сокете.

4. **`numactl --membind` вредит при высокой плотности рангов.** Принудительное размещение всех процессов на одном NUMA-узле создаёт конкуренцию за один контроллер памяти и один кэш L3.

5. **Формула оптимальной конфигурации** для данной архитектуры и стенсила:

\[
N_{\text{рангов}} = N_{\text{NUMA}}; \quad N_{\text{OMP}} = \frac{N_{\text{ядер/сокет}}}{2}; \quad W_{\text{сум}} \leq \frac{C_{L3}}{2}
\]

где \(W_{\text{сум}} = N_{\text{рангов/сокет}} \times N_{\text{OMP}} \times W_{\text{поток}}\) — суммарный рабочий набор на сокет.

## 8. Рекомендации для следующих испытаний

- [ ] **1 MPI × 8 OMP** — чистый OpenMP без MPI-коммуникаций. Рабочий набор: \(8 \times 1{,}25 = 10\) МБ — превышает эффективный L3 (6 МБ). Гипотеза: производительность будет ниже 2×4 из-за вытеснения кэша.
- [ ] **1 MPI × 12 OMP** — все физические ядра одного сокета. Рабочий набор: \(12 \times 1{,}0 = 12\) МБ — превышает L3. Гипотеза: дальнейшая деградация.
- [ ] **2 MPI × 6 OMP** — 12 ядер, 240 слоёв/ранг. Рабочий набор: \(6 \times 1{,}5 = 9{,}0\) МБ — превышает эффективный L3 (6 МБ), но меньше физического (12 МБ). Гипотеза: производительность между 2×4 и 3×4.
- [ ] Повторить 2×4 с явной привязкой `I_MPI_PIN_DOMAIN=[0xFFFF,0xFFFF0000]` + `OMP_PROC_BIND=close` для подтверждения воспроизводимости.
- [ ] Установить sampling-драйвер VTune для получения hardware event metrics (LLC misses, memory bandwidth).
- [ ] Профилировать 2×4 через wrapper для проверки баланса вычислений/коммуникаций в оптимальной конфигурации.

## 9. Практические выводы для OpenFOAM

- Для сеток 5+ млн ячеек на NUMA-серверах с ограниченным L3 предпочтительна схема с минимальным числом MPI-рангов (по числу NUMA-узлов) и умеренным числом OpenMP-потоков (половина ядер на сокет). Это максимизирует локальную область и удерживает рабочий набор в L3.

## Приложение C. Проблемы окружения

### C.1. VTune + Intel MPI Hydra — конфликт ptrace/dup2

```
[proxy:0:0@kol-serv] HYD_spawn: dup2 error (Device or resource busy)
```

VTune перехватывает файловые дескрипторы через ptrace; Hydra выполняет `dup2` при spawning рангов — конфликт. Обходной путь: wrapper-скрипт, запускающий ранг 0 под VTune, остальные — напрямую.

### C.2. NUMA-миграция потоков

При 6×2 потоки мигрируют между NUMA-узлами. `I_MPI_PIN_DOMAIN=node0` не всегда предотвращает миграцию. Рекомендуемая привязка:

```bash
export I_MPI_PIN=on
export I_MPI_PIN_DOMAIN=[0-11]
export I_MPI_PIN_ORDER=compact
export OMP_PROC_BIND=close
export OMP_PLACES=cores
```

### C.3. VTune без драйвера sampling

Используется user-mode sampling (`-knob sampling-mode=sw`). Драйвер sampling не установлен — недоступны hardware events и microarchitecture insights.
